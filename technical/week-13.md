### **📚 Конспект для студентов: Финальный проект. Неделя 2: Разработка ядра**

**Цель недели:** Превратить спроектированные на прошлой неделе типы в работающие модули бизнес-логики, используя Utility Types для создания гибкого и безопасного API.

#### **1. Напоминание: что такое Utility Types?**
Это встроенные в TypeScript "инструменты" для преобразования одних типов в другие. На этой неделе они — ваши главные помощники.
*   `Partial<T>`: Делает все свойства типа `T` **необязательными**.
*   `Required<T>`: Делает все свойства типа `T` **обязательными**.
*   `Pick<T, K>`: Создаёт новый тип, взяв из типа `T` только указанные свойства `K`.
*   `Omit<T, K>`: Создаёт новый тип, **исключив** из типа `T` указанные свойства `K`.
*   `ReturnType<F>`: Получает тип возвращаемого значения функции `F`.

#### **2. От интерфейсов к модулям: архитектурный подход**
Ваш файл `src/types.ts` — это **контракт на данные**. Модуль — это **исполнитель**, который работает по этому контракту.
*   **Принцип модульности**: Создайте отдельный файл (например, `src/core/TaskManager.ts`), который будет отвечать **только за бизнес-логику** (добавление, удаление, поиск задач).
*   **Чёткое API**: Экспортируйте из модуля только те функции (или класс), которые должны быть видны снаружи. Их сигнатуры должны максимально использовать ваши типы.

#### **3. Практика: применяем Utility Types в реальном коде**
Рассмотрим на примере модуля управления финансами (`FinanceManager`).

```typescript
// Файл: src/types.ts
export interface Transaction {
  id: string;
  amount: number;
  category: string;
  date: Date;
  description?: string;
}

// Файл: src/core/FinanceManager.ts
import { Transaction } from '../types';

export class FinanceManager {
  private transactions: Transaction[] = [];

  // 1. Partial<T> для обновления
  // Мы можем обновить только несколько полей транзакции, а не все сразу.
  updateTransaction(id: string, updates: Partial<Omit<Transaction, 'id'>>) {
    // ... логика поиска по id и применения updates
  }

  // 2. Pick<T, K> для возврата конкретных данных
  // Часто клиенту нужна не вся транзакция, а только её часть.
  getTransactionSummary(id: string): Pick<Transaction, 'amount' | 'date' | 'category'> | null {
    // ... логика поиска и возврата конкретных полей
  }

  // 3. ReturnType для явного указания типа
  // Допустим, у нас есть внутренняя сложная функция для расчёта.
  private calculateComplexReport(): { total: number; tax: number } {
    // ... сложные вычисления
  }
  // Мы можем использовать её тип возврата для другой функции.
  getAnnualReport(): ReturnType<FinanceManager['calculateComplexReport']> {
    return this.calculateComplexReport();
  }
}
```

**Ваша задача:** Продумать, где в логике **вашего** проекта такие приёмы сделают код более удобным и надёжным. Например, `Partial<...>` отлично подходит для функций редактирования, а `Pick<...>` — для функций, возвращающих сводки или данные для отображения в списке.

#### **4. Ключевые шаги для этой недели**
1.  **Создайте новый файл(ы)** для модулей бизнес-логики (например, в папке `src/core/`).
2.  **Импортируйте** ваши типы из `src/types.ts`.
3.  **Реализуйте 2-3 ключевые функции** (например, "добавить элемент", "найти элемент", "получить статистику").
4.  **Спросите себя:** "Можно ли улучшить сигнатуру этой функции с помощью `Partial`, `Pick` или `Omit`?".
5.  **Экспортируйте** только публичное API вашего модуля.

#### **5. Контрольное задание К13.1**
**Задача:** Реализовать ядро вашего проекта — 2-3 ключевых модуля с бизнес-логикой.

**Требования:**
1.  Модули должны быть созданы в отдельном файле (или файлах) в проекте.
2.  Модули должны импортировать и использовать типы, спроектированные на прошлой неделе (из `src/types.ts`).
3.  **Обязательное условие:** В коде модулей **должно быть как минимум два разных примера использования** изученных Utility Types (`Partial`, `Required`, `Pick`, `Omit`, `ReturnType`).
    *   *Пример 1:* Функция обновления, принимающая `Partial<YourType>`.
    *   *Пример 2:* Функция, возвращающая `Pick<YourType, 'field1' | 'field2'>` для отображения в списке.
4.  Код должен компилироваться без ошибок (`tsc --noEmit`).
